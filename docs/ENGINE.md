# Insidir financial intelligence engine

This document covers the backend engine. The website in `web/` is described in [WEBSITE.md](WEBSITE.md); the engine serves it on every non-API path.

## Implemented
- SEC current-filings Atom feed ingestion with declared User-Agent, rate control, bounded fetches, retry/backoff, and safe SEC URL allowlisting.
- EDGAR accession directory and Form 4 ownership XML parsing. **P/A non-derivative purchases** and **S/D sales** are distinguished from awards, exercises, derivative trades and other events.
- PostgreSQL persistence, accession deduplication, transactional writes, ingestion audit records, and a Postgres advisory lock to prevent overlapping workers.
- Subscriber API for recent filings, complete filing transactions, issuers, insiders, transaction filters, and descriptive distinct-owner purchase grouping.
- **Personnel files**: one reporting person's public SEC record by owner CIK (`GET /v1/people/<cik>`, `src/person-profile.mjs`), behind `person.html?cik=…`. Joint filings (several reporting owners on one Form 4) are attributed to every owner through `sec_filing_owners`, so people who only file jointly have a file, can be followed and show up in the followed feed.
- Read-only SEC intelligence: official company ticker-to-CIK lookup, filings by company via Submissions API, and financial measures from XBRL Company Facts API. Each observation links to the originating document; no predictive advice is computed.
- **Paywall with a paid trial** (`src/paywall.mjs`, `src/billing.mjs`): no free tier. A new subscription starts with a 7-day trial for $1, then renews at $39/month through Stripe. Every product page and every product API needs a signed-in account with an active or trialing Insidir Pro subscription or a complimentary owner/team email.
- **Public insider pages** (`src/public-pages.mjs`): server-rendered `/insider-trading`, `/insider-trading/<TICKER>` and `/insiders/<cik>-<name>` from the Form 4 import, plus `/sitemap.xml` and `/robots.txt`, readable without an account. See [Public insider pages](#public-insider-pages). See [Hard paywall and billing](#hard-paywall-and-billing).
- Email/password sessions (salted scrypt), email verification, password recovery and change, sign-out of other devices, a security log, data export, watchlists, and account deletion that cancels the Stripe subscription first. **Signup is disabled by default.**
- **Research events** (`src/research-events.mjs`): normalized, deduplicated events from the import (purchases and sales per Form 4, Form 4/A comparisons, multi-insider purchase groups, watched companies' other SEC filings) with trade, filing and retrieval times kept apart; **sourced explanations** (`src/explanations.mjs`, AI part off by default); **alerts** in the app and by consented email (`src/notifications.mjs`). Configuration and operations: [OPERATIONS.md](OPERATIONS.md).
- Optional read-only SnapTrade OAuth (scope exactly `read`) with PKCE S256, random user-bound and expiring state, encrypted tokens, rotated refresh tokens, on-demand brokerage positions, user-initiated revocation and privacy-preserving instrument normalization. Requires an approved SnapTrade OAuth app.
- Explicit source registry; House/Senate, social, crypto ingestion are blocked pending licensing/legal review.
- Optional automatic poller (every 2 minutes by default, `INSIDIR_INGEST_EVERY_MIN`) or secured on-demand/cron ingestion.

## Setup
1. Provision PostgreSQL and provide DATABASE_URL.
2. Set SEC_USER_AGENT to a **real organization name and monitored contact email**; do not use the example address.
3. Set ALLOWED_ORIGINS to the HTTPS origins of the Insidir website. Keep COOKIE_SECURE=1 in production.
4. Run npm install, npm run migrate, npm test. After upgrading an existing database to `sql/008_filing_owners.sql`, run `npm run backfill-owners` once (see [Joint filings](#joint-filings-sec_filing_owners)).
5. Run npm start. AUTO_INGEST=1 enables ingestion every 2 minutes (INSIDIR_INGEST_EVERY_MIN) inside a single always-on service; alternatively use an external scheduled task with INGEST_SECRET and POST /v1/internal/ingest.
6. Configure the paywall and Stripe billing (next section). The paywall is on by default: until billing is configured, nobody except the accounts in `INSIDIR_COMPLIMENTARY_EMAILS` can use the product.
7. Set ALLOW_SIGNUP=1 once billing works end to end; people create an account first and subscribe on `/subscribe.html`.

Run npm run ingest for a manual ingestion. This fetches up to 35 current filings by default; it is not a complete history backfill. Already parsed accessions are skipped.

## Source-backed research and review journal
The `/research.html?ticker=AAPL` page organizes imported SEC Form 4 activity and its original filing references. Each transaction distinguishes the underlying transaction date from the filing's publication date, including transaction codes, derivative classification and amendments. Empty datasets are shown as unavailable rather than replaced with sample signals.

Signed-in users may save a private research status (`researching`, `watching`, `passed`) and up to 1500 characters of notes. Run `npm run migrate` on deployment to create `research_decisions` from `sql/003_research_decisions.sql`. The data is tied to the authenticated user and is deleted with the user account. Requests are same-origin only for writes.

The public-company intelligence brief uses `GET /v1/intelligence?ticker=AAPL`, returning selected 8-K, 10-K, 10-Q, proxy and beneficial-ownership disclosures, four reported XBRL measures (when available), and a chronological evidence brief combining SEC filings with already imported Form 4 transactions. Ticker mapping uses the SEC official `company_tickers.json`, not fuzzy company-name matching. The shared SEC client uses host/path allowlists, the configured real operator User-Agent, throttling, bounded responses, retry handling and 15-minute memory caching (ticker mapping for 24 hours). No scraped document text or AI-generated interpretation is presented. API responses explicitly report missing facts and coverage caveats.

There is **no brokerage integration, trade execution, trade recommendation engine, live quote feed or automatic strategy** in this release. Reviews are user-authored notes; they never place orders. Future brokerage workflows require a trading-capable partner, explicit consent, guardrails and financial-regulatory review.

## Hard paywall and billing
Insidir is a paid product with **no free tier**; a subscription starts with a **7-day trial for $1** (see [Paid trial](#paid-trial)). `src/paywall.mjs` holds the rules as pure functions (`classifyPage`, `classifyApi`, `hasAccess`, `accessSummary`, `safeNext`, `gate`); `src/api.mjs` runs `gate()` on every request, before it serves a page, a company report endpoint, billing or any other API. `test/paywall.test.mjs` covers the rules end to end without a database.

**Access** means the account's `users.subscription_status` is `active` or `trialing`, **or** its email is listed in `INSIDIR_COMPLIMENTARY_EMAILS` (comma-separated, case and spaces ignored; for the owner and team). `past_due`, `unpaid`, `incomplete`, `paused`, `canceled` and no subscription do not have access. **With the paywall on and billing not configured, nobody but complimentary accounts can use the product, and nobody can subscribe.**

| Requests | Signed out | Signed in, no access | Access |
| --- | --- | --- | --- |
| Product pages: `dashboard`, `research`, `explore`, `company`, `filings`, `filing`, `people`, `person`, `watchlist`, `portfolio`, `alerts` (GET/HEAD, with or without `.html`, any query; `next=/person.html?cik=1214156` is a valid return path) | 302 → `/signin.html?next=<path+query>` | 302 → `/subscribe.html?next=<path+query>` | served |
| Account pages: `subscribe`, `billing`, `account` | 302 → `/signin.html?next=…` | served | served |
| Public pages (`index`, `platform`, `why-insidir`, `data`, `pricing`, `company-info`, `terms`, `privacy`, `signin`, `signup`, `404`, `account-deleted`) and every asset | served | served | served |
| Product API: `/v1/filings*`, `/v1/transactions`, `/v1/companies`, `/v1/clusters`, `/v1/insiders`, `/v1/people/*`, `/v1/status`, `/v1/search`, `/v1/intelligence`, `/v1/market/chart`, `/v1/company/*`, `/v1/me/watchlist*`, `/v1/me/research-decisions*`, `/v1/me/manual-holdings*`, `/v1/me/people*`, `/v1/me/alerts`, `/v1/me/brokerage/*` (except the deletes in the next row) | 401 `{error, signin:"/signin.html"}` | 402 `{error:"An active Insidir subscription is required", subscribe:"/subscribe.html"}` | handled |
| Deleting your own data: `DELETE /v1/me/brokerage` (revokes the read grant), `DELETE /v1/me/watchlist/{ticker}`, `DELETE /v1/me/people/{cik}`, `DELETE /v1/me/manual-holdings/{ticker}`, `DELETE /v1/me/research-decisions?ticker=` | 401 `{error, signin:"/signin.html"}` | handled | handled |
| Open API: `/v1`, `/v1/sources`, `/healthz`, `/v1/auth/*`, `GET`/`DELETE /v1/me`, `/v1/billing/*`, `/v1/internal/ingest` (its own bearer secret) | handled | handled | handled |

- Removing your own data never needs a subscription: a member whose subscription has lapsed can still revoke a brokerage grant and delete saved items one by one (reading or adding them still needs access). This is the one deliberate exception to "`/v1/me/*` is product data".
- Redirects carry `Cache-Control: no-store`. Everything served past the gate to a signed-in visitor (product data, product and account pages) is rewritten to `Cache-Control: private, …` (or stays `no-store`) with `Vary: Cookie`, so a CDN or shared cache placed in front of the engine can never replay one member's response to a visitor the gate would stop. Public pages and assets keep their normal caching; `npm run web` is not gated and keeps `public`.
- If the session cannot be checked (for example the database is unreachable) gated requests stay closed: product and account page navigations get a readable 503 HTML page ("Back in a moment", a *Try again* link to the same page, `no-store`, `Retry-After: 30`) and gated API calls get 503 JSON. Public pages and assets still work because they never touch the session. Page paths are matched the way the static server resolves them (percent-decoding, dot segments, trailing slashes, any letter case), so an encoded path cannot reach a product page. Any `/v1` route that is not listed as open is treated as product data (fail closed).
- The brokerage OAuth callback (`/v1/me/brokerage/callback`) is a browser navigation, so it redirects like a page (`next=/portfolio.html`) instead of answering 401/402.
- `next=` values are only ever same-origin relative paths to known product or account pages, optionally with a query (`/company.html?ticker=AAPL`); absolute and protocol-relative URLs, backslashes, fragments, dot segments, encoded paths and unknown pages are rejected (`safeNext`). Pages must validate `next` the same way before navigating.
- One database query per request: `currentUser()` returns the subscription fields with the session and is memoised for the request, so the gate and the handler share it. Public pages and assets never touch the session.
- `INSIDIR_PAYWALL=0` turns gating off (local development only; the engine logs a warning at startup). Any other value, including unset, keeps it on. `npm run web` (no database) stays ungated for design previews.

`GET /v1/me` (never gated) returns:

```json
{"user":{"id":"…","email":"…"},
 "access":{"active":true,"plan":"pro","status":"active","billingEnabled":true,"complimentary":false,"currentPeriodEnd":"2026-11-14T00:00:00.000Z"}}
```

`active` is whether the account can use the product right now (always true when `INSIDIR_PAYWALL=0`); `plan` is `pro` only for a Stripe subscription in good standing (`none` otherwise, including complimentary accounts); `status` is the raw Stripe status or null. `POST /v1/auth/login` and `POST /v1/auth/register` return the same `access` object next to `user`, so the sign-in page can choose between the product and `/subscribe.html` without another request.

### Billing endpoints (signed in; no subscription needed)
- `GET /v1/billing/status` → `{billingEnabled, plan:"pro"|"none", active, complimentary, subscriptionStatus, currentPeriodEnd, hasCustomer}`. `?refresh=1` re-reads the customer's subscriptions from Stripe first (rate-limited); call it on `/billing.html?checkout=success` in case the webhook has not arrived yet.
- `POST /v1/billing/checkout` → `{url}` of a Stripe Checkout page for the configured Price. Success returns to `/billing.html?checkout=success`, cancel to `/subscribe.html?checkout=cancel`. An account's first checkout carries the paid trial (below). Requests must come from `INSIDIR_PUBLIC_URL`'s origin. To prevent double billing:
  - For an account that already has a Stripe customer, the engine **re-reads the customer's subscriptions from Stripe first** (and stores the result), so a checkout that completed before its webhook arrived counts. It refuses with 409 while any subscription for the configured Price can still bill: `active`/`trialing` (manage it instead), `past_due`/`unpaid` (update the payment method in the portal), `incomplete` (first payment still being confirmed) or `paused`. If Stripe cannot be read, it answers 503 and starts nothing. A customer that no longer exists in this Stripe account (e.g. test data after switching to live keys) is replaced by a new one.
  - Any earlier **open** Checkout page of the customer is expired before a new one is created, so only the newest can be paid.
  - One billing change per account at a time: a second checkout (or an account deletion) while one is being prepared answers 409.
- `POST /v1/billing/portal` → `{url}` of the Stripe customer portal (cancel, update card, invoices); returns to `/billing.html`.
- `POST /v1/billing/webhook` — Stripe events, verified with the signing secret (5-minute tolerance, rolled secrets accepted) and processed once per event ID. For each event the engine **re-reads the customer's subscriptions from Stripe** and stores the one in the best standing, so late or out-of-order events cannot lock out a paying member or keep a cancelled one in. Only subscriptions to the exact `INSIDIR_STRIPE_PRICE_ID` grant access; others are stored as `inactive`. A failed update forgets the event so Stripe's retry is processed.

### Account deletion
`DELETE /v1/me` makes sure nothing in Stripe can bill the account again **before** anything is deleted. It does not rely on the subscription ID saved by the webhook, which can be missing or stale (webhook not yet delivered or misconfigured, or more than one subscription on the customer):
1. If the account has a Stripe customer, every **open Checkout page** of that customer is expired (`POST /v1/checkout/sessions/{id}/expire`), so a payment completed later cannot start a subscription for a deleted account.
2. The engine asks Stripe for **all of the customer's subscriptions** (`GET /v1/subscriptions?customer=…&status=all`, every page) and cancels every one that can still bill (any status except `canceled` and `incomplete_expired`: active, trialing, past_due, unpaid, incomplete, paused), **whatever its Price**, with `DELETE /v1/subscriptions/{id}`.
3. Fallback: the saved subscription ID is cancelled too if Stripe did not list it for the customer.

If Stripe cannot confirm any step (unreachable, not configured, an error, a list it cannot read in full), the account is **not** deleted and the endpoint returns 503 with a message the page shows; every cancellation Stripe did accept stays cancelled, and trying again finishes the job. A customer that does not exist in the configured Stripe account cannot bill from it, so that case does not block deletion. Then the engine revokes an active brokerage grant, deletes the user (sessions, watchlist, notes, holdings and follows cascade) and clears the cookie: `{deleted:true, subscriptionCanceled:boolean}`. Cancellation is immediate and Stripe issues no automatic partial refund. The Stripe customer record and its invoices stay in Stripe for accounting.

Safety net: if an Insidir checkout (its metadata names the Insidir account) still completes after that account was deleted, the `checkout.session.completed` webhook cancels the new subscription and logs a warning so the operator can refund the first invoice. Checkouts that Insidir did not create on the same Stripe account are never touched.

### Paid trial
An account's first checkout starts with a trial: Stripe Checkout charges a one-time **$1** line item (`price_data`, no extra Stripe product needed) and sets `subscription_data[trial_period_days]=3`; a card is always collected (`payment_method_collection=always`) and, if none is on file when the trial ends, the subscription is cancelled. Stripe's own submit text states the terms: "$1 today for 7 days of Insidir. Unless you cancel before the trial ends, Insidir Pro then renews at $39 a month." A trialing subscription has full access (`ACCESS_STATUSES`), and `current_period_end` is the trial's end.

One trial per account: no trial when `users.trial_started_at` is set (stamped the first time a subscription is seen `trialing`, never reset; `sql/010_paid_trial.sql`) or when the Stripe customer has ever had a subscription for the configured Price. Those checkouts charge $39 at once.

| Variable | Default | Meaning |
|---|---|---|
| `INSIDIR_TRIAL` | on | `0` switches the trial off (every checkout charges $39 at once). |
| `INSIDIR_TRIAL_DAYS` | `7` | Trial length for new checkouts, clamped to 1–14 days. Running trials keep the end date Stripe set at their checkout. The site, terms and emails say 7 days; ops raises an alert if this differs. |
| `INSIDIR_TRIAL_FEE_CENTS` | `100` | The one-time trial fee in US cents, clamped to 50–3900. |

Creator commissions (`CREATORS.md`) are earned on the first $39 payment: after a trial that is the first renewal (`billing_reason=subscription_cycle`); the $1 trial invoice never qualifies, and the unique `referred_user_id` keeps later renewals out.

### Stripe setup
1. In Stripe create the product "Insidir Pro" with one recurring Price of $39.00 USD per month; copy its `price_…` ID. Do not put a trial on the Price: the engine adds the paid trial at checkout.
2. Add a webhook endpoint `https://YOUR_DOMAIN/v1/billing/webhook` for `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `customer.subscription.paused`, `customer.subscription.resumed` and `invoice.paid` (creator commissions); copy its signing secret.
3. Configure the customer portal (cancellation, payment method updates, invoice history).
4. Set the variables above, `INSIDIR_BILLING_ENABLED=1`, then `ALLOW_SIGNUP=1`. Test a full signup → checkout → dashboard → cancel → deletion cycle in Stripe test mode before switching to live keys.

## Public insider pages
`src/public-pages.mjs` renders plain HTML (no script needed) from the engine's Form 4 import, so search engines and signed-out visitors can read it; the product stays behind the paywall and every page ends with the trial offer.

- `GET /insider-trading`: the biggest open-market purchases and sales of the last 30 days (codes P and S, non-derivative, original filings), the newest filings and the most active companies.
- `GET /insider-trading/<TICKER>`: one company's 40 newest Form 4 lines, 90-day totals from original filings (Form 4/A restatements are listed, not added up again) and its reporting people. `nvda` and `BRK.B` redirect to `NVDA` and `BRK-B`; a ticker with no imported lines is a `noindex` 404.
- `GET /insiders/<cik>-<name-slug>`: one reporting person from `personProfile()` (companies and roles, totals, 30 newest lines), with no new SEC requests. A bare or stale slug redirects (301) to the canonical one.
- `GET /sitemap.xml` (index) → `/sitemaps/pages.xml`, `/sitemaps/companies-N.xml`, `/sitemaps/insiders-N.xml` (40,000 URLs each), absolute URLs on `INSIDIR_PUBLIC_URL` (default `https://insidir.com`).
- `GET /robots.txt`: everything allowed except `/v1/` and the product and account pages; names the sitemap.

Pages do not depend on who is asking: they are cached in memory for 10 minutes (3,000 entries) and sent with `Cache-Control: public, max-age=600`. Uncached renders are limited to 90 a minute per client address. `src/paywall.mjs` classifies all of these paths as public. Values are shares × the price the filer reported; nothing is estimated.

## Manual portfolio (no brokerage or vendor account)
Manually entered stock tickers and share counts work with existing user accounts and PostgreSQL. No paid market-data API or brokerage permissions are needed. The portfolio page shows these entries **above** the optional SnapTrade section. Each ticker links to its SEC Research Desk, and the page displays the most recent imported ownership transaction in the past 30 days when available. This is a ticker-only matching aid, not proof of security identity or a recommendation.

Run `npm run migrate` (server startup migrates automatically) to create `manual_holdings` from `sql/005_manual_holdings.sql`. API: `GET /v1/me/manual-holdings`; `POST /v1/me/manual-holdings` JSON `{"ticker":"AAPL","quantity":"2.5"}` to create/update; `DELETE /v1/me/manual-holdings/AAPL` to remove. All endpoints require a signed-in session with an active subscription (except `DELETE`, which only needs a sign-in so a lapsed member can still remove entries); writes require the existing same-origin CSRF check. Holdings are private and automatically deleted with the user account. A user can store up to 100 entries with 8 decimal places of share precision. No prices or portfolio values are estimated. **Leave BROKERAGE_CONNECT_ENABLED=0** until a paid vendor connection is desired and configured.

## Read-only brokerage connections (optional)
This feature is OFF by default (`BROKERAGE_CONNECT_ENABLED=0`). It relies on SnapTrade **OAuth Apps** and a user's pre-existing **SnapTrade Personal** connections, not Commercial user-secret registration or direct Fidelity credentials. Create a Test app in the SnapTrade Dashboard, register the exact callback URI `https://YOUR_DOMAIN/v1/me/brokerage/callback`, and obtain a client ID and client secret. Test OAuth apps are limited to five users; production usage requires approval. Set `SNAPTRADE_OAUTH_CLIENT_ID`, `SNAPTRADE_OAUTH_CLIENT_SECRET`, `SNAPTRADE_OAUTH_REDIRECT_URI`, and an independently generated 32-byte hexadecimal `BROKERAGE_ENCRYPTION_KEY`; then set `BROKERAGE_CONNECT_ENABLED=1`.

**Do not set the encryption key in a public repository.** Save it in hosting secrets, back it up securely, and do not rotate it until existing encrypted tokens can be migrated. Never use the example placeholder callback in production. Sign-in accounts must be enabled and the main server (`npm start`) must run with PostgreSQL. Migrations now include `sql/004_brokerage_oauth.sql`. `npm run web` only shows the disconnected preview.

Connection steps: signed-in user chooses Connect on `portfolio.html` → POST `/v1/me/brokerage/connect` generates a one-time PKCE and state → user consents to `read` access in SnapTrade Personal → SnapTrade redirects to `/v1/me/brokerage/callback` → server validates and consumes state, exchanges the code, verifies the granted scope, and encrypts access and refresh tokens in PostgreSQL. User shares only the accounts they authorized with SnapTrade. GET `/v1/me/brokerage/portfolio` reads investments and positions on demand without storing the account snapshot, excludes non-stock holdings from SEC ticker-based matching, and displays source-backed imported Form 4 disclosures from the last 30 days when available. Ticker matching is only a lead for manual investigation; it cannot establish security identity on its own. SnapTrade positions and quotes may be delayed and records may be incomplete.

DELETE `/v1/me/brokerage` calls the OAuth revocation endpoint before erasing stored credentials. Local account deletion also attempts to revoke active access first; if the provider cannot confirm revocation, the request fails rather than silently abandoning the grant. Users can independently revoke Insidir's access in SnapTrade Personal → Settings → Connected apps.

OAuth is strictly read-only: the authorization URL requests only `read`; the database accepts only `read`; no trading endpoints are available or called. This phase is **not** a regulated portfolio manager or execution feature. It does not provide individual trade recommendations. Get legal/compliance review and broker permissions before adding personalized advice or orders. Confirm the provider's terms, privacy and cybersecurity requirements before production. Before broad launch, add independent penetration/security review, durable audit logs, account consent tracking and integration monitoring.

API endpoints (authenticated): GET `/v1/me/brokerage/status`; POST `/v1/me/brokerage/connect`; GET `/v1/me/brokerage/callback`; GET `/v1/me/brokerage/portfolio`; DELETE `/v1/me/brokerage`. Mutations require a trusted same-origin request. No provider credentials or OAuth tokens are returned to the browser.

## API (JSON)
Every endpoint below except `/v1`, `/healthz`, `/v1/sources` and the prepared images at `/v1/media/<sha256>.<ext>` is product data: it answers 401 when signed out and 402 without an active subscription (see [Hard paywall and billing](#hard-paywall-and-billing)).
- GET /v1 – service information
- GET /healthz – database and SEC configuration check
- GET /v1/status – latest ingestion and filing count
- GET /v1/sources – source availability and permissions
- GET /v1/filings?limit=30&q=&ticker= – recent official filing metadata
- GET /v1/filings/{18-digit accession} – original record with parsed transaction rows
- GET /v1/transactions?ticker=&category=reported_purchase – a joint filing's lines (several reporting owners) have `owner_cik: null`, the owners' names joined in `owner_name`, and `owners: [{cik, name}]` (as filed, in filing order) so each owner can be linked; `GET /v1/filings/{accession}` adds the same `owners` to its joint lines
- GET /v1/companies?q= ; GET /v1/insiders?q= – reporting people, newest line first, at most 100, each once (padded and unpadded owner CIKs merged): `owner_cik` (10 digits), `owner_name`, `ticker` and `issuer_cik` of their newest line, `filings`, `last_transaction_date`; `q` matches the name filed. With `sec_filing_owners`, owners of joint filings are listed too, under the name each filed with, so a person who only files jointly can be found by the people directory and the header search
- GET /v1/people/{cik}?limit=100 – one reporting person's file (see [Personnel file](#personnel-file-get-v1peoplecik))
- GET /v1/intelligence?ticker=AAPL – selected company SEC filings, XBRL facts, original-source links, and deterministic research brief (SEC_USER_AGENT required)
- GET /v1/clusters?days=7&minOwners=2 – descriptive, not predictive; amendments can duplicate event counts
- GET /v1/search?q=nvidia – ticker and company-name lookup over the SEC's official ticker mapping (one listing per issuer for name matches; every share class for ticker matches)
- GET /v1/market/chart?ticker=NVDA&range=1Y – delayed price series (1D, 1W, 1M, 3M, 1Y, 5Y) plus the session quote (price, previous close, daily change). `MARKET_DATA_PROVIDER=none` turns market data off
- GET /v1/company/profile?ticker=NVDA – Wikidata facts matched exactly by SEC CIK (P5531): founding year, latest employee count, official website, logo, leadership and founders with Commons photos, plus the Wikipedia summary
- GET /v1/company/insiders?ticker=NVDA – the issuer's 16 most recent Form 4/4A filings parsed live from EDGAR: owner, role, transaction codes, net open-market shares, reported value and holdings after. Each activity row has `owner` (the first reporting owner) and `owners: [{name, cik, role, isDirector, isOfficer, isTenPercentOwner, entity}]` (every reporting owner in filing order; `joint: true` when there are several), and `people` lists every owner once by CIK (a joint filing counts for each of its owners, `jointFilings` says how many): people first, then funds and companies (`entity: true`; a sponsor's joint filings can list dozens of vehicles), each newest filing first
- GET /v1/company/news?ticker=NVDA – 8-K announcements with item descriptions, and publisher headlines that name the company
- GET /v1/company/logo?ticker=NVDA – 302 to the company's prepared logo (`/v1/media/<sha256>.png`), or 404 when no published logo can be verified. `variant=wide` prefers a wordmark. `X-Logo-Source` names the source
- GET /v1/company/photos?ticker=NVDA&wait=2500 – verified portraits for the company's SEC reporting people (keyed `cik:<owner CIK>`), display names, and current leadership/founders from Wikidata. Work runs in the background; `complete:false` means more sources are still being checked, and `queued:true` that the company's job is waiting for its turn (`wait` holds up to 8 s)
- GET /v1/media?tickers=AAPL,BRK.B&people=1214156:AAPL,1214156:cik:320193,1214156&ciks=1234567&wait=1200 – logos and headshots for a whole page in one request (see [Logos and headshots for a page](#logos-and-headshots-for-a-page-get-v1media))
- GET /v1/media/<sha256>.(png|webp|jpeg|svg) – prepared logos and portraits, content-addressed. Open (no sign-in) and cached publicly for a day with an `ETag` (`If-None-Match` answers 304), not for ever, so a takedown reaches caches: the address is the image's SHA-256, so it cannot be guessed, and only `/v1/media`, which is product data, hands addresses out. A taken-down address answers 404. Unknown addresses answer 404, are remembered for 5 minutes (one database lookup each), and each client may cause at most 120 such 404s a minute (then 429, before any lookup)

`/v1/intelligence` additionally returns `ttm` (trailing twelve months: latest fiscal year + current year-to-date − prior-year year-to-date), `balance` (cash and short-term investments and total debt from one balance-sheet date), `shares` (newest reported shares outstanding), `profile` (exchange, business address, fiscal year end, industry) and `currency`. US GAAP and IFRS (20-F/40-F) taxonomies are supported. The company endpoints need no database; `npm run web` serves them for previews.

### Personnel file (`GET /v1/people/<cik>`)
`src/person-profile.mjs`, served by `src/api.mjs` behind the paywall (product data: 401 signed out, 402 without access; with `INSIDIR_PAYWALL=0` it still needs a sign-in). Everything in it is a public SEC record: the person's own Form 4 lines in the engine's import, their role at each issuer as written in their latest Form 4 there, and the issuers EDGAR lists for their owner CIK. Nothing is estimated, scored, hidden or predicted.
- **Request.** `cik`: path segment of 1–12 digits; zero-padded and unpadded forms are the same person (`0001214156` = `1214156`); all zeros or anything else is 400. `limit`: transactions to return, default 100, clamped to 1–500 (blank or not an integer: 100). 404 when the CIK has no lines in parsed filings (without `sec_filing_owners` the message says joint filings are not attributed yet). 405 for methods other than GET/HEAD. 429 past 60 profiles a minute per member.
- **Response** (keys in this order; counts and sums are JSON numbers, sums added exactly in decimal and converted once; dates are ISO strings as pg returns them):
  - `person: {cik, name, filed_names}` – the owner CIK as stored by the import on the newest line (usually 10 digits; `POST /v1/me/people` accepts any form), the name as filed on the newest line, every distinct name filed under this CIK (newest first, at most 20).
  - `companies: [{ticker, issuer_cik, issuer_name, roles, first_transaction_date, last_transaction_date, last_published_at, transactions, purchases_value, sales_value}]` – one per issuer (padded and unpadded issuer CIKs merged), most recently published first, at most 100. `roles` is the relationship ticked on the person's latest Form 4 there: the officer title as filed (or "Officer"), "Director", "10% owner", else the "other" text (`ownerRoles()` in `src/insiders.mjs`, the one wording source). Read from `sec_filing_owners` when it has the person's row, else from the filing's XML for the 8 most recently published issuers only, one cached document each, within the SEC allowance below. `null` = not looked up (past those 8); `[]` when no XML is on file, on a failure, past the allowance or past the 3 s budget.
  - `totals: {all, d30}` – each `{transactions, superseded, filings, purchases: {count, shares, value}, sales: {count, shares, value}, other: {count}, first_transaction_date, last_transaction_date, last_published_at}`. `d30` counts the lines first filed in the last 30 days (a 4/A repeating an older line keeps the original's filing date), while its `filings`, `superseded` and `last_published_at` count filings published in the window.
  - `transactions` – rows like `GET /v1/transactions` items (`t.*` plus `issuer_name`, `published_at`, `is_amendment`; NUMERIC columns as pg strings) plus `superseded`, newest trade date first. Superseded lines are listed, never hidden. `owner_cik: null` marks a joint filing; with `sec_filing_owners` such a line carries `owners: [{cik, name}]`, every reporting owner of that filing as filed and in filing order (this person included), exactly as `/v1/transactions` does, so the page links each co-filer to their own file.
  - `filings: [{accession, form_type, ticker, issuer_cik, issuer_name, published_at, source_url, lines}]` – newest first, at most 100; `lines` is this person's lines in that filing.
  - `other_issuers: [{cik, name, ticker, relation, last_transaction_date}]` – issuers EDGAR's owner page lists for this CIK that are not in the import (ticker from the SEC ticker file); best effort, `[]` on failure, past the allowance or after 2.5 s.
  - `edgar_url`, `source: "SEC Form 4"`, `disclaimer: "Public SEC records. Not a recommendation or a prediction."`
- **Amendments.** A line is `superseded` when a Form 4/A published later repeats it: same issuer (padded or not), trade date, transaction code, acquired/disposed, derivative flag and shares (`SAME_LINE` in `src/person-profile.mjs`). Only the latest copy is counted, so a restated sale is one sale. A 4/A that changes any of those fields is a different line and both count. The followed feed's 30-day totals use the same rule.
- **Cost.** Four parameterised statements per request whatever the number of lines (plus one owners read by accession when the lines shown include joint ones, and the `sec_filing_owners` check, which is remembered for an hour once answered and asked again on the next request after a failure), each scoped by `owner_cik = ANY([unpadded, 10-digit])` off `sec_transactions_owner_idx`, never one per line or issuer. The SQL part of a heavy filer's profile (2,000 lines or more) is kept for 30 s. New SEC requests (uncached ownership documents and EDGAR's owner page) are bounded: at most 4 documents and 1 owner page per profile, 40 and 10 per member (else address) per 10 minutes, 60 starts a minute for all members together; none start while the shared SEC queue is longer than 2 s (`secBacklogMs()` in `src/sec.mjs`), and reading a cached lookup is free.

### Joint filings (`sec_filing_owners`)
A Form 4 can list several reporting owners (a fund, its general partner and the person who controls them). The importer stores such a filing's lines once, with `owner_cik` NULL and the owners' names joined, so market totals and the dashboard count each line once. `sql/008_filing_owners.sql` adds `sec_filing_owners`: one row per reporting owner per filing (`owner_cik` and `owner_name` as filed, and the relationship boxes: director, officer and title, 10% owner, other text), with an index by owner and a partial index on joint lines. `persistFiling` writes it in the same transaction as the lines, so every new import has it. With it:
- the personnel file attributes joint lines to every owner listed and reads roles without refetching the XML;
- `POST /v1/me/people` accepts a person who only files jointly, and their joint lines are in `GET /v1/me/people/updates`;
- `/v1/transactions`, `/v1/filings/{accession}`, the followed feed, the personnel file, `/v1/me/alerts` `/v1/me/manual-holdings` and the brokerage portfolio (`recentSecActivity`) add `owners: [{cik, name}]` to joint lines (one read by accession per answer: `withJointOwners` in `src/person-profile.mjs`);
- `GET /v1/insiders` lists joint filers under the name each filed with;
- `GET /v1/media` confirms a joint filer at an issuer from it (so their headshot can be looked for).
Each feature checks once whether the table exists (and again every few minutes while it does not; a check that fails is not remembered, so a database blip never switches attribution off), so the engine works before the migration has run.

Filings imported before the table existed are filled by `npm run backfill-owners` (`scripts/backfill-filing-owners.mjs`; needs `DATABASE_URL` and `SEC_USER_AGENT`). For each parsed filing with an XML address, no owner rows and not looked at yet (joint filings first, since only they need the table to be attributed; then newest first), it reads the filed ownership XML once through the engine's SEC client (declared User-Agent, SEC addresses only), parses it with the importer's own `parseOwnership` and, in one transaction per filing, writes the owners and a `sec_filing_owners_checked` row recording that the filing was looked at. It changes nothing else.
- **SEC fair access.** The script is a separate process, so the engine's in-process SEC throttle (a module variable in `src/sec.mjs`) does not cover it. It holds the ingest lock (`pg_try_advisory_lock(813076522)`, the one `src/ingest.mjs` takes) for the whole run, so the engine's scheduled ingest skips meanwhile (when an ingest holds it the script exits with 75 and changes nothing: run it again later); it paces its own requests to `--rate` per second (default 4, at most 8), leaving room under the SEC's 10 a second for the engine's page lookups; and it stops at the first sign of a block (`SEC responded 403`, or 429 after the client's retries) with `"stopped":"sec_blocked"`, leaving that filing for the next run. Wait at least ten minutes before running it again after a block. Ten failures in a row also stop it (`"stopped":"repeated_failures"`).
- **Progress.** A filing that fails (an XML that is gone, a parse error, a timeout) is recorded with its reason and skipped by later runs, as is a filing whose owners have no usable CIK (0 owners), so every run moves on. `--limit=N` (1–100000, default 500; written with `=`, anything else is refused), `--rate=R`, `--retry-failed` (also asks again for the failures on record) and `--dry-run` (reads and parses, writes nothing). It prints one JSON summary line: `filings`, `owners`, `joint`, `failed`, `errors`, `stopped`, `requests`, `remaining` (filings not looked at yet) and `failedOnRecord`; it exits 1 when a filing failed or the run stopped early, 2 on bad arguments.
- **Operator rule.** Run it again until `remaining` is 0 (a run that does not lower `remaining` made no progress: read its `errors`), then once with `--retry-failed` if `failedOnRecord` is above 0.

### Company report data sources
- **SEC EDGAR / XBRL** (with `SEC_USER_AGENT`): ticker map, submissions, company facts and Form 4 XML. Requests share one throttle (8 per second, below the SEC's 10-per-second limit); filed ownership documents are cached for 24 hours and summaries for 15 minutes.
- **Yahoo Finance public chart and news endpoints**: delayed prices and headlines, cached 1–60 minutes by range. These endpoints are unofficial; review Yahoo's terms and switch to a licensed market-data vendor before relying on them commercially. Set `MARKET_DATA_PROVIDER=none` to hide prices.
- **Wikidata (CC0) and Wikipedia (CC BY-SA 4.0)**: profile facts, leadership and descriptions. The page attributes Wikipedia text and links to the source. Profiles are cached for 24 hours.

### Logos (`src/logo-resolver.mjs`)
Every SEC-listed company gets its real logo shown on the page background with no tile or box, or no logo at all. Candidates come from stock-logo libraries (stockanalysis light/dark, companiesmarketcap), the company's Wikipedia infobox and Wikidata logo (matched by CIK), then the company's own website (JSON-LD, header logo, touch icon; domain verified from SEC filings) and FMP, EODHD and nvstly. Those three key images by ticker alone, so their logo is shown only when another source shows the same mark. A Wikipedia or Wikidata logo whose file is named for one of the company's SEC former names and not its current one is the old identity and is not used (`staleNameFile`: Wikipedia kept Skillz's mark on the article for Firy Inc. after the June 2026 rename). `LOGO_OVERRIDES` in the resolver holds corrections found by auditing a 120-company sample (and WGO, whose stock-logo file is the bare ticker letters) (the company's own file, or no logo when every source shows another company); operator overrides in the store take precedence. A candidate is used only when the identity is safe: recycled tickers and recent rebrands (SEC former names, new 8-A12B/424B4 filers) need shape agreement (IoU ≥ 0.5 on 48×48 ink masks) between independent sources. The chosen file is prepared server-side with sharp (`src/image-analysis.mjs`): a uniform tile around the mark is keyed out, ink that would vanish on the dark page is lifted (near-black becomes off-white, dark brand colours keep their hue), and the result is trimmed. Logos that are a badge by design stay as drawn. Results are cached 30 days (1 day when a better source was unreachable, 7 days for "no logo").

### People photos (`src/people-photos.mjs`)
Each person shown on the report gets a real photo or keeps initials; faces are never generated or guessed. Sources, strongest first:
1. Wikidata/Commons people linked to the company or its notable subsidiaries by statements (CEO, chair, board, officer, founder, employer, position held), EntitySearch with a statement tie, and Wikipedia search whose article links to the company. Only free-licence files, credited.
2. The company's own leadership and board pages (domain verified from SEC filings; robots.txt and crawl-delay respected; bot walls end the crawl).
3. Headshots printed in the company's latest SEC proxy statement (DEF 14A), paired by alt text and caption layout.
4. The same person's captioned headshot in another company's proxy where they also file as an insider (tied by SEC owner CIK).
Commons answers first; when the company's page or proxy also has the person, that official headshot replaces the Commons picture. Every match uses one strict name matcher (`src/person-match.mjs`: surname plus given name, nickname or 3+ letter prefix, no conflicting middle initial) and must be tied to the company; a name alone never attaches a photo. A verified photo is reused wherever the same owner CIK files. Portraits are cropped to 256 px WebP. Company results are cached 7 days, person photos 90 days.

Sources audited as not being photographs are listed in `src/photo-exclusions.mjs` (Reddit's 2026 proxy prints illustrated avatars of its directors; one passed every automated check). Nothing from them is used, and records stored before an entry was added stop being served (`GET /v1/media`, `GET /v1/company/photos`). Owners whose filed name is a company or fund never get a face; the short suffixes S.A., AG, N.V. and Co count only when dotted or after the first word, because SEC files people surname first ("Sa Neto Francisco" is Francisco Sá Neto).

`node scripts/audit-media.mjs --sec` writes a contact sheet of every stored photo and logo against the SEC names, flagging the same image on two people, a caption that is not the filer, a face on a company or fund, an excluded source and a Wikipedia logo named for a former company name. Run it against the production database after large imports and check every card by eye: no rule can tell a well-drawn illustration from a photo, or a ticker-letter placeholder from a real wordmark.

### Logos and headshots for a page (`GET /v1/media`)
`src/media-batch.mjs`. One request answers every company and person on a page from what the resolvers above have already decided, and never waits on an upstream source. Anything not decided yet is listed as pending and resolved in the background, so a page shows the issuer's logo (or a placeholder) and swaps the headshot in when it lands.
- **Request.** `tickers` (≤ 60; `BRK.B` is read as `BRK-B`), `people` (≤ 100 entries, CIKs with or without leading zeros, in three forms: `ownerCik:TICKER`, the reporting owner and the issuer they file for; `ownerCik:cik:issuerCik`, the same for an issuer known only by CIK; `ownerCik` alone, when no issuer is known), `ciks` (≤ 60 issuer CIKs for companies without a ticker) and `wait` (0–1500 ms: logos already resolving may land in this response). Invalid entries are dropped and echoed in `invalid`; more than a limit, or nothing valid, is a 400. 120 requests per minute per IP.
- **Response.**
  - `logos[TICKER]` or `logos["cik:<CIK without leading zeros>"]`: `{src, w, h, source, name, alt?: {src, w, h}}`. The square variant is the main one when it exists and the wide wordmark is `alt`; a `cik:` entry of a listed company also carries its `ticker`. The issuer of every person, and a listed company that files as an owner, always get an entry.
  - `photos[<owner CIK>]`: `{src, w: 256, h: 256, source ("wikimedia" | "company-site" | "sec-proxy"), credit, sourceUrl, name?}`.
  - `owners[<owner CIK>]`: `{entity: true, ticker}` when the filer is a fund or company, not a person (`ticker` when it is itself listed, so the page can show its logo).
  - `null` means resolved and nothing exists: the page moves down its chain (headshot → issuer logo → initials).
  - `pending: {logos: [key], photos: [entry]}` lists what is still resolving; a photo entry is listed in the form it was asked (`"<owner>:<TICKER>"` or `"<owner>:cik:<issuer>"`, without leading zeros). `retryAfterLogos` and `retryAfterPhotos` (seconds; 0 when that kind has nothing pending) say when to ask again for each kind on its own: logos settle within seconds (3), a photo job takes longer (8, or 15 while one waits its turn). `retryAfter` is the slower of the two, for older clients.
  - `queued: [entry]`: the pending photo entries whose company job is still waiting for its turn (not running yet). A client should keep asking for these without counting the polls against its patience (the website allows about 15 minutes): a cold page with many new companies can take several minutes to reach them.
  - **People forms.** `ownerCik:cik:issuerCik` answers the issuer's logo as `logos["cik:<issuer CIK>"]` (with its `ticker` when listed) and looks for the photo at that issuer: a listed issuer gets a company job exactly like the ticker form; an unlisted one (photo jobs read the SEC listing) answers from the person's `person-photo` record or `null`, with no job. `ownerCik` alone answers from the `person-photo` record (or `owners` when the CIK is itself a listed company), never starts a job and is never pending; without a usable record nothing was looked for, so `photos[<owner CIK>]` is left out of the answer rather than `null` (which would read as "no photo exists" and be remembered by the page), except after a takedown, which is `null`. One owner asked several ways in one request gets one answer: a photo from any entry wins, then pending, then `null`.
  - `Cache-Control: no-store` while anything is pending, otherwise `private, max-age=300`.
- **Logos.** A key with no decision starts `logoForTicker` (or `resolveLogo` by CIK) in a limiter: 4 at a time, at most 20 new per request, one per CIK however many tickers share it. An issuer in `ciks` is looked up only when it is in the SEC ticker file or the engine's import has filings for it (`loadIssuers`: `issuer_cik` in `sec_filings` or `sec_transactions`); any other number is `null` with nothing started (the website preview has no database, so there only listed CIKs resolve). A resolution that finds nothing without being able to check every source (which the resolver does not cache) is answered `null` for 15 minutes; a resolver error stays pending and is retried after a minute. A chosen logo whose bytes are no longer stored is resolved again rather than served.
- **Photos.** A `person-photo` record (a verified photo is reused at every company where that owner CIK files) answers at once. Otherwise the issuer's `company-photos` record decides: a finished job that had the person on its roster and found nothing is `null`. A company with no finished job is queued (see below). With the engine's database, a pair starts or extends a company job only when the SEC import confirms that the owner filed for that issuer (`loadOwnersFrom` in `src/media-batch.mjs`, called from `src/api.mjs`: one `SELECT DISTINCT ON (owner_cik, ticker, issuer_cik)` over `sec_transactions` for the whole request, matching the issuer by ticker or by CIK, plus the same over `sec_filing_owners` for joint filers when that table exists) or the company's finished roster already has them (it is built from the issuer's last 16 Form 4 filings); the job then gets the name from the import. Any other pair is `null` with no job started, whatever state the company's record is in; it is pending only while a job that someone else started for that company is under way, since that job's roster may include them. Names never come from the request: `person-photo` is global by CIK, so a typed name could attach the wrong face to someone's CIK for every member. If the import cannot be reached, unconfirmed pairs stay pending and nothing starts. The website preview has no database, so there a company's own roster job may start and only the SEC's roster is used.
- **Takedowns.** `blockPersonPhoto(cik, {reason})` in `src/people-photos.mjs` (operators, e.g. `node -e 'import("./src/people-photos.mjs").then(m => m.blockPersonPhoto("1214156", {reason: "…"})).then(r => { console.log(r); process.exit(0); })'` with `DATABASE_URL` set) writes `person-photo-override:<CIK>` = `{none: true}`, stops serving every image chosen for that person (`media-blocked:<sha>`, re-read by each instance every 5 minutes) and rewrites the finished `company-photos` records that name them, keeping their expiry. Both `/v1/media` and `/v1/company/photos` also drop the photo, the display name taken from it and the matching leadership portrait of anyone with an override on every answer, so an override written straight into `media_records` takes effect at once as well.
- **Allowances.** New upstream work is budgeted per requester (the signed-in member, else the client address) per 10 minutes: 60 logo resolutions and 10 company photo jobs from `/v1/media`, and 20 report photo jobs from `/v1/company/photos`. Joining work that is already resolving is always free; past the allowance a key stays pending until the window turns.
- **Photo job queue** (`src/people-photos.mjs`). At most 2 company jobs run at once across the process, plus one slot that only a company report someone has open (`/v1/company/photos`, "page" priority) may use, so the report's job starts at once even behind a dashboard's batch; the rest wait (`/v1/company/photos` answers `queued:true`, `/v1/media` lists them in `queued`). Order: report pages, then other pages, then the warm-up; within a priority the requester served least recently goes first, and one requester may hold at most 10 waiting jobs (the logo limiter does the same with 60), so one member or one cold page cannot hold the queue for everyone else. Opening the report of a company whose job is waiting raises that job to the report's priority. A request for a waiting company merges its people into that job; one for a running company is picked up by a quiet re-run right after it. A re-run adds people to a finished company: it reuses every source's cache, keeps the finished record in place until it is done, and runs at most once per person per company every 6 hours. Each finished record keeps its `roster`, the filers that are `entities`, and the verified `extras` so later runs keep them. At most 10 new company jobs start per `/v1/media` request.
- **Warm-up** (`src/media-warm.mjs`). After each SEC import that parsed filings, the engine sends the companies and reporting owners filed in the last 20 minutes through the same queues at low priority, so logos and roster photos are usually ready before anyone opens the dashboard, and the database keeps them across restarts.

### Media store
Prepared images live in `entity_media` (sha256, bytes) and decisions in `media_records` (`sql/007_entity_media.sql`), with a bounded in-memory cache in front, so restarts and extra instances do not refetch third-party sources. Without `DATABASE_URL` everything works from memory. Third-party image fetches are https-only, public-address-only (re-checked on each redirect), size-limited and byte-sniffed; SVGs with scripts or external references are rejected. Image responses carry a sandbox CSP.

## Account API
Mutations require a trusted Origin header. Registration requires ALLOW_SIGNUP=1. `/v1/auth/*`, `GET /v1/me`, `DELETE /v1/me` and `/v1/billing/*` work without a subscription; the `/v1/me/*` endpoints below need one (402 otherwise), except their `DELETE`s and `DELETE /v1/me/brokerage`, which any signed-in account may call to remove its own data.
- POST /v1/auth/register, POST /v1/auth/login (both return `{user, access}`), POST /v1/auth/logout
- GET /v1/me → `{user:{id,email}, access}`; DELETE /v1/me cancels the Stripe subscription first, then deletes the account
- GET /v1/me/watchlist, POST /v1/me/watchlist with JSON {"ticker":"AAPL"}, DELETE /v1/me/watchlist/AAPL
- GET /v1/me/people (followed reporting people, newest follow first, one row per person: `owner_cik`, `created_at`, `owner_name`, `ticker`, `last_transaction_date`, `last_published_at`), POST /v1/me/people with JSON {"owner_cik":"1214156"} (404 if the CIK is not in imported records, 409 beyond 150 follows, 429 when follow attempts are too frequent), DELETE /v1/me/people/1214156
- GET /v1/me/people/updates?limit=40 (1-100): `people` — each followed person (most recently active first) with `owner_name`, `ticker`, `issuer_name`, `last_published_at`, `last_transaction_date`, `last` (their newest transaction line), `filings_30d`, `transactions_30d`, `purchases_30d_value`, `sales_30d_value`; `items` — the newest transaction lines by anyone followed, newest publication first; `following` — the count
- **One owner CIK per person.** POST stores the 10-digit form whatever the client sends (`1214156`, `0001214156` and `000001214156` are one person) and answers with the stored row; a person already followed in another form (rows from before this rule) is answered with that row and nothing is added. The duplicate check, DELETE (which removes every stored form) and every read compare without leading zeros, and answers give `owner_cik` in the 10-digit form. A person's lines are read in both forms off `sec_transactions_owner_idx`.
- **Joint filers** can be followed once `sec_filing_owners` exists: their joint lines count for them in the list and the feed, and every joint line in `items` and `last` carries `owners: [{cik, name}]`. The overview shows a joint line under the followed person's own name followed by "and N others" (a link to the filing, which lists every owner); elsewhere it leads with the first individual owner.
- **Restated lines count once.** The 30-day totals use the personnel file's rule (`SAME_LINE` and `SUPERSEDED` from `src/person-profile.mjs`): a line repeated by a later Form 4/A counts once, on the date it was first filed, so a restated old trade does not enter the window; `filings_30d` counts filings published in the window. `items` lists every line as filed.
- **Cost.** At most three statements (plus the owners of joint lines in one more), never one per person. Each followed person is read in one pass over their parsed lines; at most the 150 newest follows are read before any per-person work. On PostgreSQL 16 with 200,000 filings and 800,000 lines, 150 follows of about 160 lines each answer in about 0.15 s for `people` and 0.15 s for `items`. The engine's connections run with `jit=off` (`src/db.mjs`): JIT compilation added 0.6–1.4 s to these statements (unless `DATABASE_URL` carries its own `options`).
- GET /v1/me/research-decisions?ticker=AAPL; POST /v1/me/research-decisions with JSON {"ticker":"AAPL","reviewStatus":"watching","notes":"Read the original filing"}; DELETE /v1/me/research-decisions?ticker=AAPL
- GET /v1/me/alerts – watchlist Form 4 matches computed on demand (kept for older clients)
- GET /v1/me/notifications?unread=1&before= ; POST /v1/me/notifications/read {ids|all} – alerts from research events
- GET/POST /v1/me/email-preferences – in-app on/off, event types, email off/immediate/daily (turning email on needs `{consent:true, consentVersion}`)
- GET /v1/research-events?ticker=&owner=&type=&before= ; GET/POST /v1/research-events/{id}/explanation (POST takes `{question}`)
- POST /v1/auth/verify-email {token}, POST /v1/auth/resend-verification, POST /v1/auth/forgot-password {email} (always 202), POST /v1/auth/reset-password {token,password}

Session tokens are random; their SHA-256 digests live in PostgreSQL. Cookies use HttpOnly/Secure/SameSite=Lax. Rate limits are shared by every instance through PostgreSQL (`src/rate-limit.mjs`, keys stored as digests). Admin routes need a token and a one-time code (`src/admin-auth.mjs`).

## Compliance gates
- SEC fair-access guideline: declare user agent; keep requests below its limit; use caching; identify original filing and distinction between trade and publication dates.
- Do **not** scrape, commercialize, or republish congressional personal financial disclosures until counsel confirms use rights and data permissions. This code does not fetch them.
- Do not scrape Truth Social, X, or other social services without licensed/authorized access.
- Do not associate anonymous crypto wallets with politicians without strong verifiable evidence.
- Paid investment advice, personalized signals and compensation for securities analysis can implicate securities regulations; get relevant review before enabling.

## Deployment
Deploy this repository as **insidir-engine** on Railway, connected to Railway PostgreSQL. Set DATABASE_URL to a Railway PostgreSQL reference variable and provide the SEC operator identity. The same service serves the website from `web/` (the API lives under `/v1`), so sign-in cookies and API calls stay same-origin. The pages call the API with relative `/v1/...` paths, so if `web/` is hosted elsewhere, put it behind a reverse proxy that forwards `/v1` to this engine on the same domain.

## Honest limitations
- Tests use synthetic fixtures, not claims about current transactions.
- Live SEC fetching, data completeness, and outage recovery need verification in production.
- The original issuer search and Form 4 database cover imported data only; the intelligence ticker lookup covers the current official SEC mapping, which the SEC says may be incomplete.
- SEC company facts and company submissions may be temporarily unavailable, outdated, or lack a particular ticker or metric; the interface states the limitation rather than inventing results.
- Grouping may double count amended filings. It is not an investment forecast.
- The paywall trusts Stripe's subscription status as stored by the webhook (or `?refresh=1`, or a checkout attempt). If webhooks are not delivered and nobody refreshes, a cancellation reaches Insidir late; Stripe retries failed webhooks for three days. Account deletion and checkout do not depend on the stored status: they re-read Stripe.
- The one-billing-change-per-account lock is per process (rate limits are shared, this lock is not); Insidir runs as a single service. With several instances, the Stripe re-reads, the expiry of earlier open Checkout pages and the orphaned-checkout safety net still apply.
- Account deletion treats a customer that does not exist in the configured Stripe account as unable to bill. If the secret key belongs to a different Stripe account than the one that billed the customer, cancel that subscription in the right Stripe dashboard.
- Email verification exists but is only enforced once an email provider is configured (or `INSIDIR_REQUIRE_EMAIL_VERIFICATION=1`); until then a complimentary address must be registered by its owner before it is listed.
- No personalized trading advice, autonomous strategies, licensed political feed, crypto watcher, social scan, or push notifications have been activated. Read-only brokerage access requires configuration and real integration tests; it is not live by default.

**AI cost architecture** (`src/ai-gateway.mjs`): one explanation per (source, content SHA-256, explanation type,
prompt version, model, language), shared by every member; concurrent requests for the same key are coordinated in
PostgreSQL (one claims the row, the others wait for it); a changed source hashes to a new key. Every provider call
writes `ai_usage` with the provider's token counts and, when reported, its cost (`usage.include`); list-price
estimates are stored separately as `estimated`. Global hourly/daily call limits, per-member hourly/daily limits,
daily and monthly USD budgets, input/output caps, a timeout and one retry are enforced before every call. The
inexpensive model handles single-source explanations; the stronger model is used only for multi-company or
multi-person syntheses.

**Form 13F** (`src/form13f.mjs`): EDGAR submissions → `index.json` → `primary_doc.xml` (cover and summary totals) →
information table. Values are normalised to dollars (filings before 2023-01-03 reported thousands); parsed rows and
value are compared with the cover page's `tableEntryTotal` / `tableValueTotal` and stored as `completeness`. Each
filing is stored once by accession with a content hash. Manager names always come from EDGAR.
